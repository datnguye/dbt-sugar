dbt sugar Architecture

How sugar works behind the page, from sugar starting up to a Diff click in the browser. Pick a flow and press play, or step through it. The spec is the contract; this page is the map, and when the two disagree, the spec wins.

    Layers

    Dependencies point one way, and npm run check fails the build when they don't. The page imports only its own files.

    Where data lives

    • Your project (logs/, target/): read, never written. Sugar's own dbt runs log to logs/sugar-<time>-<pid>/.
    • ~/.dbt-sugar (or $DBT_SUGAR_HOME): history.duckdb, runs/<project>/ with the last 10 invocations, and base/<sha>/ with parsed manifests per commit.
    • Per invocation: run.json, the matching manifest.json and run_results.json, and its slice of dbt.log.
    • Memory only: the live snapshot and the last 10 invocations' log lines (5000 each).

    Boundaries

    • The server binds loopback, refuses unknown Host headers and needs the per-launch token on POST.
    • No outbound network. Git refs from the page must match a strict pattern before they reach git.
    • One runtime dependency, @duckdb/node-api, imported only by history/store.js. If it can't load, Live keeps working.
    • Git is only asked to resolve refs and add or remove a detached worktree in a temp folder; dbt is only asked to parse.
